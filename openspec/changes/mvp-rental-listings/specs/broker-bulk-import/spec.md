# Broker Bulk Import Specification

## Purpose

A broker whose account has been explicitly enabled by the operator uploads a CSV describing their portfolio. Valid rows become **drafts**; photos are attached afterwards through the same presigned-upload path the single-listing flow already uses. The CSV never carries images, and the import never becomes a way around `listing-publication`.

## Non-Goals

Self-service enablement, XLSX or JSON input, ZIP archives, photo URLs fetched by the server, scheduled or API-driven imports, editing existing listings through import, bulk delete.

## Requirements

### Requirement: Operator-Granted Access

The system MUST gate bulk import behind a per-account flag (`bulk_import_enabled`) that defaults to disabled and can only be changed by the operator. The system MUST enforce this flag server-side on every import endpoint. Hiding the user interface MUST NOT be the only control.

#### Scenario: Account without the flag cannot reach the feature

- GIVEN an authenticated broker whose account has `bulk_import_enabled = false`
- WHEN they send a request directly to any bulk import endpoint, bypassing the user interface
- THEN the system rejects the request as forbidden and creates no draft

#### Scenario: Enabled account sees the feature

- GIVEN an authenticated broker whose account has `bulk_import_enabled = true`
- WHEN they open their publisher area
- THEN the bulk import entry point is available to them

### Requirement: Downloadable Template as the Format Contract

The system MUST offer a downloadable CSV template generated by the same code that parses uploads. The template MUST contain the exact expected header row, at least one example row, and the currently valid city and zone values.

#### Scenario: Template matches the parser

- GIVEN the operator has added, removed, or renamed an accepted column
- WHEN a broker downloads the template
- THEN the template header reflects the change without any separate document being edited

#### Scenario: Template is accepted when filled and re-uploaded

- GIVEN a broker who downloads the template, replaces the example rows with their own data, and saves it unchanged otherwise
- WHEN they upload that file
- THEN the system parses it without format errors

### Requirement: Accepted CSV Structure

The system MUST require a header row and MUST accept columns in any order. The system MUST require the columns `referencia_externa`, `titulo`, `descripcion`, `precio_usd`, `ciudad`, and `zona`. The system MUST ignore unrecognised columns rather than mapping them onto any field.

#### Scenario: Missing required column is rejected before any row is processed

- GIVEN an uploaded file whose header omits `precio_usd`
- WHEN the file is submitted
- THEN the system rejects the whole file with a message naming the missing column, and creates no draft

#### Scenario: Unknown columns are ignored, not mapped

- GIVEN an uploaded file containing extra columns such as `publisher_type`, `status`, `expires_at`, or `user_id`
- WHEN the file is processed
- THEN those columns are ignored, and the resulting drafts take their publisher type from the importing account and their status from the system

### Requirement: Encoding and Delimiter Tolerance

The system MUST accept both comma and semicolon as field delimiters, detecting which is in use. The system MUST tolerate a leading UTF-8 byte order mark. The system MUST require UTF-8 content and MUST reject a file whose encoding cannot be decoded as UTF-8, with a message telling the broker how to re-export.

#### Scenario: Semicolon-delimited export from a Spanish-locale spreadsheet is accepted

- GIVEN a file exported by a spreadsheet configured for a Spanish locale, using `;` as the delimiter and carrying a UTF-8 byte order mark
- WHEN it is uploaded
- THEN the system parses the columns correctly rather than reading the file as a single column

#### Scenario: Non-UTF-8 file is rejected with actionable guidance

- GIVEN a file saved in a legacy single-byte encoding whose accented characters cannot be decoded as UTF-8
- WHEN it is uploaded
- THEN the system rejects the file and states that it must be saved as CSV UTF-8

### Requirement: Whole-File Validation Before Any Write

The system MUST validate every row before creating any draft. The system MUST NOT write partial results while parsing.

#### Scenario: A late invalid row does not leave earlier rows written

- GIVEN a file whose last row carries an invalid price
- WHEN validation runs
- THEN no draft exists for any row of that file until the broker confirms the preview

### Requirement: Preview and Confirmation with Per-Row Errors

The system MUST present a preview reporting the count of valid rows and, for each invalid row, its row number and the reason it failed. The system MUST create drafts only after the broker explicitly confirms the preview, and MUST create drafts only for the valid rows.

#### Scenario: Partial file is imported after confirmation

- GIVEN an uploaded file with 38 valid rows and 2 invalid rows
- WHEN the broker reviews the preview and confirms
- THEN the system creates 38 drafts and reports the 2 failed rows with their row numbers and reasons

#### Scenario: Preview alone creates nothing

- GIVEN a broker who uploads a file and receives the preview
- WHEN they abandon the flow without confirming
- THEN no draft was created

### Requirement: Idempotent Import by External Reference

The system MUST treat `referencia_externa` as unique per importing account. Re-importing a row whose `referencia_externa` already exists for that account MUST NOT create a duplicate listing.

#### Scenario: Re-uploading the same file creates no duplicates

- GIVEN a broker who has already imported a file and had its drafts created
- WHEN they upload the identical file again and confirm
- THEN the system creates no additional drafts and reports the rows as already imported

#### Scenario: Duplicate reference within a single file is rejected

- GIVEN an uploaded file containing the same `referencia_externa` on two rows
- WHEN validation runs
- THEN both rows are reported as invalid and no draft is created for either

### Requirement: Drafts Are Not Published Listings

The system MUST create imported rows in a draft state that is excluded from search results, has no revealable contact, and is not subject to the 30-day expiry clock. A draft MUST become active only once it satisfies minimum publishable content and passes trust checks.

#### Scenario: Draft is invisible to tenants

- GIVEN an imported draft with no photos attached
- WHEN a tenant searches the draft's city and zone
- THEN the draft does not appear in the results

#### Scenario: Expiry clock starts at activation, not at import

- GIVEN a draft created by import
- WHEN it is later activated
- THEN its 30-day expiry is measured from activation

### Requirement: Photos Attached Through the Existing Upload Path

The system MUST attach photos to imported drafts through the same presigned upload and trust pipeline used by the single-listing flow. The system MUST NOT accept image bytes inside the CSV, and MUST NOT fetch images from URLs supplied in the file.

#### Scenario: Duplicate photo rules still apply to imported drafts

- GIVEN a broker attaching a photo to an imported draft that perceptually matches a photo belonging to a different publisher
- WHEN activation is attempted
- THEN the system rejects it under the same cross-account duplicate rule the single-listing flow applies

#### Scenario: Photos cannot be attached to another account's draft

- GIVEN broker A holding a draft
- WHEN broker B attempts to attach a photo to broker A's draft
- THEN the system rejects the attempt

### Requirement: Bounded Input Size

The system MUST enforce a maximum file size and a maximum row count, both rejected before parsing begins.

#### Scenario: Oversized file is refused before parsing

- GIVEN an uploaded file exceeding the configured size or row limit
- WHEN it is submitted
- THEN the system rejects it without parsing its contents and states the applicable limit

### Requirement: Generated CSV Output Is Not Executable

The system MUST neutralise leading `=`, `+`, `-`, and `@` characters in any field it writes into a downloadable CSV, including the template and any error report.

#### Scenario: Formula-like value is neutralised on export

- GIVEN stored data whose value begins with `=`
- WHEN it is written into a CSV the system offers for download
- THEN the emitted field cannot be interpreted as a formula by a spreadsheet application
